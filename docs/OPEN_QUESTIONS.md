# Open questions

Raised while building the Operations Platform, in the same stop-and-ask spirit as the ecosystem's own
`docs/OPEN_QUESTIONS.md`. Each needs a human decision. Nothing below has been guessed.

| ID | Raised | Question | Why it matters | Current behaviour |
| -- | ------ | -------- | -------------- | ----------------- |
| OPQ-001 | 2026-10-24 | **Credentials.** Which GitHub token (fine-grained, read-only on the ecosystem repo) and which Anthropic API key should the server use? | Live connector, webhook and narrative need them. | Not set. Connector degrades to the committed snapshot and lists its errors. Local deterministic engine is used for narrative. |
| OPQ-002 | 2026-10-24 | **Sign-in / SSO.** How should staff authenticate (the ecosystem uses Keycloak)? | Approval is recorded against a typed name; the server's publish gate trusts its own warehouse, which any client can append to. | **Interim (2026-10-25):** `OPS_USERS` gives each person a token and the server derives the actor from it; appends are validated server-side; publishing needs an authenticated user. Still open: SSO (Keycloak?), token rotation/revocation, and roles (who may approve what). Do not expose publicly until decided. |
| OPQ-003 | 2026-10-24 | **Outbound channels.** Should the platform ever send email, WhatsApp or post to social? | POPIA s69 and consent evidence are needed first. | Not built. Drafts are downloaded and sent by a human. |
| OPQ-004 | 2026-10-24 | **Payments and invoicing.** Which provider and VAT treatment? | Finance currently models from typed inputs only. | Not built; calculators only. |
| OPQ-005 | 2026-10-24 | **Agent roster discrepancy.** 56 contract files are counted in `packages/agents`; `docs/AGENTS.md` says "Fifty-five"; a marketing artefact says 46. Which is authoritative? | Any external claim about the number of agents. | Warning in the Command centre; OPS-AI-01 drafts the reconciliation. |
| OPQ-006 | 2026-10-24 | **Pricing framing.** Reconcile pricing language in marketing artefacts with the approved price list. | The platform generates no prices. | No prices anywhere in the platform. |
| OPQ-007 | 2026-10-24 | **Tenant data.** Should any aggregate (not learner-level) usage ever flow to the platform? | Needs a new de-identification path and a POPIA assessment. | Out of scope. Connector reads the repository only; learner data is refused. |
| OPQ-008 | 2026-10-24 | **Ecosystem writes.** Enable `OPS_ALLOW_ECOSYSTEM_WRITES` so an approved proposal can open an issue? | Needs Issues: write on the token. | Disabled by default; downloading the issue text always works. |
| OPQ-009 | 2026-10-24 | **True PDF.** Is "print to PDF" from HTML acceptable, or should the server render PDFs? | A server renderer adds a browser dependency. | HTML print dialog ("Save as PDF"). |
| OPQ-010 | 2026-10-24 | **Warehouse of record.** Keep JSON-lines files, or move to the ecosystem's Postgres with row-level security? | Durability, backup, multi-user access. | JSON-lines under `data/warehouse` (gitignored) or browser storage. |
| OPQ-011 | 2026-10-24 | **Ecosystem OQ-036** (MFA not shown as enforced in the Keycloak realm) was raised in the ecosystem repo today. Does Security own the follow-up? | Security of school admin accounts. | Surfaced in Security widgets; OPS-SEC-03 drafts the control mapping. |
| OPQ-012 | 2026-10-25 | **Who owns the ledger chain?** **Resolved 2026-11-03: the server.** Clients send an action to `POST /api/ledger`; the server assigns `seq`, `prevHash`, `hash` and the time under a lock, persists the entry, and returns it with any entries the client missed. `/api/warehouse/ledger` is closed to clients. | Multi-user audit ledger. | Two people working at once no longer fork the chain (tests: unit, client, end-to-end). Open dev mode still uses it; a purely local (no server) browser session still builds its own chain. Trade-off: a ledger write is now a network call that can fail and surfaces as an error on that action. |
| OPQ-013 | 2026-10-25 | **Erasure requests.** **Built 2026-11-12 with a default, needs your confirmation:** any signed-in person can raise a request; a *different* person must decide it; approving requires retyping the subject reference (checked against a stored hash) and then applies the tombstone. Only a hash of the reference is stored; the reference and note are refused if they contain a name, email, phone or ID number. Still open: (1) should only certain roles decide (e.g. the Information Officer; needs OPQ-002 roles)? (2) POPIA response deadlines and reminders are not modelled, since they are a legal determination; (3) a tombstone blocks *future* processing only: removing data already held (artefacts, Brain facts) is a separate manual step today. | POPIA s24 requests. | Two-person flow live in the UI under Core → Erasure requests, enforced on the server too. |
| OPQ-014 | 2026-11-12 | **Illustrative defaults are not facts.** The deterministic engine (used when no model is ready) and some tool defaults contain made-up specifics: sample school names ("Strelitzia Primary School"), preset numbers (4000, 12, 30), a 18.50 exchange rate, "approx R850/mo" hosting, and statements such as "AWS af-south-1 in-country hosting". They are marked `illustrative_defaults` but "Apply to Form" can still copy them into a draft. Should they be removed, replaced with blanks that name the source needed, or sourced from a ratified Brain fact? | The platform's own rule is no invented numbers. | Flagged as drafts; model output is claim-checked, deterministic output is not. |
| OPQ-015 | 2026-11-12 | **Who may attest or revoke a model provider?** Anyone signed in can. Should it be restricted to certain roles (for example the Information Officer), and should attesting need two people? | Provider terms are a legal and security judgement. | Any signed-in person; recorded in the ledger by name. **Mechanism built (2026-11-12):** set `OPS_ROLES=id:officer` and only officers can attest; unset keeps today's behaviour. Who the officers are is yours to decide. |
| OPQ-016 | 2026-11-12 | **Live provider verification.** The adapters have only been tested against local stand-ins. Who runs *Test* against the live Anthropic and Gemini accounts, and what is the correct current default Gemini model? | Request shapes could differ from the live APIs. | `docs/MODEL_HUB.md` says so; the hub's Test button is the check. |
| OPQ-017 | 2026-11-12 | **Independence of signers.** Today approver and countersigner must be different people, and the author may be one of them (so two-person teams can work). Should the author be barred from signing their own work, or should a third person be required for certain agents (finance, legal, security)? | Four-eyes versus workable for a small team. | Two distinct humans; author may be one. |
| OPQ-018 | 2026-11-12 | **What is "relevant" to ingest?** Every ratified artefact is ingested (library plus a Brain episode) unless its agent contract says `ingestion: 'none'`. Which agents' output should not be ingested (for example one-off outbound messages)? | Library and Brain should hold knowledge, not noise. | Default ingest; no agent opts out yet. |
| OPQ-019 | 2026-11-12 | **Who may run autonomy?** Anyone signed in can propose, pause or revoke a standing order, and anyone but the proposer can activate it. Should activation be limited to certain roles (for example the Information Officer for any agent touching personal-data topics), and should some agents never be allowed to run autonomously (legal, finance)? | Autonomy multiplies the effect of one mistake. | Two distinct people; everyone else can stop it. **Mechanism built (2026-11-12):** with `OPS_ROLES` set, only an officer can activate; pause and revoke stay open to all signed-in people. |
| OPQ-020 | 2026-11-12 | **Fixed inputs only.** Autonomous runs use the inputs typed when the order was made, never anything from the trigger, so they cannot be steered by an attacker who controls a GitHub event. The cost is that agents that need fresh input each time can't run on their own. Is that the right trade, or should reviewed, de-identified trigger data be allowed for chosen agents? | Prompt-injection safety versus usefulness. | Fixed inputs only. |
| OPQ-021 | 2026-11-12 | **Quarantine policy.** A failed draft stays a draft for a person to fix. Should repeated failures from one order pause it automatically? | Stops a broken order from filling the board. | Not automatic; shown on the board and in recent runs. |
| OPQ-022 | 2026-11-12 | **Agent owners.** Every contract now names an accountable owner *role*. Today it defaults to the department head ("Head of Finance"), which is a placeholder. Who really owns each agent, and who owns the cross-cutting ones (AI, Security)? | An owner is who answers for an agent's drafts. | Placeholder roles; the contract check only requires that a role (not a person) is named. |
| OPQ-023 | 2026-11-12 | **Provider limits for sensitive agents.** The contract can restrict an agent to named providers (`models`), but no built-in agent does yet. Which agents (legal, finance, security) should be limited to a provider whose terms you have reviewed? | Provider terms differ on retention and training use. | No agent restricted; every attested provider may serve every agent. |
| OPQ-024 | 2026-11-13 | **Who reviews the legal documents?** 65 of the 120 library documents are drafting outlines that name a reviewer (an attorney, the Information Officer, the tax adviser, a labour-law practitioner, the security lead or the school's safeguarding lead). Who is the company's attorney and tax adviser, and who is the Information Officer? | Contracts, notices and POPIA documents must not be used unreviewed. | Marked DRAFT with a visible review note; nothing is approved for use. |
| OPQ-025 | 2026-11-13 | **When is the library seeded?** `npm run seed:library` is run by hand. Should the server seed on first start, or only on an administrator's request? | Seeding on start is convenient but writes to the warehouse without a person choosing to. | Manual and idempotent. |
| OPQ-026 | 2026-11-13 | **Provisional figures in the quote calculator and invoice templates.** Rates are the proposed school pricing (decision D-1, provisional). Tax-invoice wording depends on VAT registration (D-6). Confirm both before any document goes to a school. | A quote or invoice is a commitment. | Calculator reads `SCHOOL_PRICING` and says "Provisional pricing"; the invoice template says to use it only once VAT-registered. |
